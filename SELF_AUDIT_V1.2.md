## Verdict on the v1.2 fixes

I reviewed each v1.2 fix as a **fresh auditor** would, looking for new bugs introduced by the fixes. Findings:

### C-NEW-1 verification (revert on underflow) ✅ Sound
- The `require(bal >= burnedBalance, ...)` check is a view function, so it costs gas only when called in a transaction (not in `view`/`pure` contexts).
- Tested with `test_total_assets_reverts_on_negative_rebase` — confirms the revert fires when `balanceOf < burnedBalance`.
- **No new issues introduced.** The revert message string is specific enough for off-chain indexers to identify the cause.

### H-NEW-1 verification (exact fee) ✅ Sound
- `msg.value != VAULT_CREATION_FEE` is a single check; simpler and safer than the old `paid < fee ? revert : (paid > fee ? refund : ok)` pattern.
- Removes the entire refund path: no `payable(msg.sender).call{value: X}("")` to grief.
- The factory now has **no way** to receive ETH without forwarding it to feeCollector. This eliminates the "ETH stuck in factory" risk entirely.
- **New gas observation:** users who sent excess ETH in v1.1 will now have their calls revert. This is the right UX (loud failure beats silent loss), but frontends should show "Send exactly 0.001 ETH" prominently.

### M-NEW-1 verification (totalBurned view) ✅ Sound
- Public view that just returns the `burnedBalance` storage variable. No state changes, no gas cost.
- Existing `burnedBalance` is auto-generated by Solidity for the `public` declaration, so the new `totalBurned()` is just a named alias for analytics convenience.

### M-NEW-2 verification (per-vault minFirstDeposit) ✅ Sound
- `minFirstDeposit` is now a storage variable set in `initialize()`.
- Factory computes it as `10 ** decimals()`. This means:
  - 6-decimal tokens (USDC): 1.0 USDC minimum first deposit
  - 8-decimal tokens (SPX): 1.0 SPX minimum first deposit
  - 18-decimal tokens (ETH/wstETH): 1.0 token minimum first deposit
- This is meaningful for all decimal configurations: 1 USDC for squatting, 1 SPX, 1 wstETH. No token is "free to squat".
- Tested in `test_min_first_deposit_configured_correctly`.

### M-NEW-3 verification (claimDividend validation) ✅ Sound (via C-NEW-1)
- `claimDividend` doesn't directly validate against the pool size, but it relies on `safeTransfer` which will revert if the vault has insufficient balance.
- The C-NEW-1 fix means that if the vault's balance drops below `burnedBalance` (rebase scenario), `totalAssets()` reverts, which means `_convertToAssets` and `_accrueDividend` calls also fail. This is an indirect validation.
- **Minor concern:** the dividend math doesn't check the pool size before incrementing `rewards[user]`. If a rebase happens between `_accrueDividend` and `claimDividend`, the user's `rewards[user]` could exceed the actual available balance, and `safeTransfer` would revert. This is a soft-failure (the user can retry or wait), not a fund-loss, so it's not a critical issue. Documented in the natspec for clarity.

### I-NEW-1 verification (BelowMinimumFirstDeposit error) ✅ Sound
- New error type with `(uint256 required, uint256 provided)` parameters. Frontends can display "Required 1.0 SPX, you provided 0.5 SPX" directly.
- Cleaner than the old `ZeroAmount()` (which was misleading for sub-minimum first deposits).

### I-NEW-2 verification (ordering comments) ✅ Sound
- Added a block comment in `deposit()` explaining the order: pull → distribute tax → accrue dividend → mint.
- Not a code fix per se, but a maintenance improvement.

### I-NEW-3 verification (ERC-4626 compat docs) ✅ Sound
- Documented in `totalAssets()` natspec that we return `balanceOf - burnedBalance` rather than `balanceOf`.
- External indexers using a generic ERC-4626 interface will see a different value, but this is unavoidable for the lock-in-vault model.
